КАК ЧИТАТЬ КОНТЕКСТ (JSON, передаётся вместе с этим заданием):
- time_range: границы теста — start_iso/end_iso (локальное время с указанием смещения) и duration_min.
- load_steps[]: ступени нагрузки. Для ступенчатого теста границы взяты из детектора ступеней по назначенной
  RPS-метрике (rps_level — уровень нагрузки, stable — была ли ступень стабильной); иначе это равные интервалы
  времени. У каждой ступени есть index, label, start_iso/end_iso и minute_from/minute_to от начала теста.
  plateau_start_iso/plateau_end_iso — плато ступени, на котором держался rps_level; drop_iso — момент, когда RPS
  упал внутри ступени и уже не вернулся к прежнему уровню. RPS ступени — это только rps_level (он же в label);
  не подменяй его средним по ступени. after_drop=true — ступень после такого падения (деградация или спад
  нагрузки): это не уровень, который выдержала система. dip=true — кратковременная просадка: RPS упал и вернулся
  к прежнему уровню, это не отдельная ступень нагрузки и не предел системы. Флаги есть только у таких ступеней.
  Ссылайся на ступени по label (например «ступень 3 · ≈150 RPS» или «интервал 2 · 10:20–10:30»).
- sections[]: группы метрик домена (label — название запроса). В каждой:
  * top_series[] — статистика серий за весь тест: mean, min, max, last, change_pct (изменение между началом и
    концом теста в %), max_time_iso/min_time_iso и max_minute_from_start. У серий нагрузочного инструмента может
    быть stable_max (уровень последней стабильной ступени) и step_segments (сегменты детектора с теми же
    флагами after_drop и dip).
  * anomalies[] — отклонения, найденные программно относительно ступеней. У каждого step_anomalies[].kind:
    elasticity — метрика выросла заметно быстрее нагрузки между ступенями (load_change_pct — рост нагрузки);
    drift — метрика изменилась на плато одной ступени при неизменной нагрузке;
    shift — интервал заметно отличается от первого (для тестов без ступеней).
    Поля value/reference/change_pct и explanation уже содержат готовую формулировку.
- step_table[]: для каждой секции — серии, ранжированные по величине изменения между ступенями
  (change_vs_first_pct), и per_step[] = {step, mean, p95, max, samples} по каждой ступени. Значения посчитаны по
  плато ступени. Если после плато RPS упал или тест закончился, в per_step есть after_plateau = {mean, min, max,
  samples} — значения после плато: деградацию после плато описывай по ним (например «на ступени 11 · ≈258 RPS после
  плато RPS упал до min»), а не как уровень ступени. Это основной источник чисел для находок: указывай ступень и
  значение из per_step.
- baseline: предыдущий прогон того же сервиса (run_name, verdict) и его статистика по тем же сериям:
  baseline_mean/baseline_p95/baseline_max и delta_mean_pct/delta_max_pct — изменение текущего прогона относительно
  него в %. Если available=false, причина указана в reason — сравнение с прошлым прогоном недоступно, не выдумывай его.
- timeline (только в итоговом задании): матрица «метрика × ступень» по всем доменам (mean_per_step — средние по плато
  ступени) — используй её, чтобы связывать события разных компонентов по одной и той же ступени.
- deterministic_sla (в итоговом задании): результат программной проверки SLA — verdict, checks[] с actual/threshold
  и passed. Это источник истины по SLA; не пересчитывай его и не противоречь ему без явной причины.
- designated_peak_performance (в итоговом задании): единственный источник максимальной производительности
  (stable_max). Не бери RPS из других доменов для оценки максимума.
- sla_step (в заданиях по доменам): ступень, на которой программно проверено SLA, — step_label, start_iso/end_iso,
  rps и checks[] с threshold/actual/passed. Статус домена определяй по ступеням до конца sla_step включительно.
  Деградацию на следующих ступенях описывай находками с её start_time (где и из-за чего система упёрлась), но не
  ставь из-за неё «Провал»: в ступенчатом тесте это ожидаемый итог. «Провал» — только если проблема началась до
  конца sla_step. Если sla_step нет, оценивай весь тест.
- system_context: справочное описание системы; используй как контекст, не как факты о метриках.
Все числа в ответе берутся только из этого контекста: если значения нет в top_series / step_table / anomalies /
baseline / timeline / deterministic_sla / sla_step — его нельзя указывать.
