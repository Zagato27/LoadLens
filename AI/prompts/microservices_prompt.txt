ЗАДАЧА: анализ метрик микросервисов в ходе нагрузочного теста.

ДАННЫЕ ДОМЕНА (какие секции могут присутствовать):
- Среднее время обработки запросов по микросервисам (rate(sum)/rate(count)).
- Количество запросов в секунду по микросервисам и суммарный RPS.
- aux_resources: CPU процесса и heap из домена JVM для сопоставления по времени.

ФОКУС АНАЛИЗА:
1. Латентность по ступеням для каждого сервиса: на какой ступени время обработки начало расти быстрее нагрузки
   (anomalies.kind=elasticity, step_table.per_step). Укажи ступень и RPS этой ступени из load_steps или секции RPS.
2. Сравнение сервисов между собой на одной ступени: кто деградирует первым, у кого латентность стабильна. Стабильные
   сервисы — одна общая находка со severity=low, без перечисления каждого.
3. Дрейф внутри ступени (anomalies.kind=drift) при неизменной нагрузке — риск накопления (очереди, пул соединений);
   отделяй его от роста между ступенями.
4. Связь с ресурсами: если в aux_resources CPU или heap растут на той же ступени, где растёт латентность, отметь
   это как совпадение по времени (не как доказанную причину).
5. Если задан baseline — сравни латентность и RPS сервисов с предыдущим прогоном (delta_mean_pct).

ОГРАНИЧЕНИЯ:
- В этом домене НЕ добавляй поле peak_performance и не делай выводов о максимальной производительности системы —
  это делается только по домену lt_framework.
- В каждой находке: микросервис (component), ступень или интервал по label, число латентности и/или RPS из контекста;
  порог — только из блока ориентиров.
- Единицы: время обработки указано в тех единицах, что в названии секции (обычно секунды); не пересчитывай без
  явной причины.
- aux_resources (CPU процесса и heap из JVM) — только для сопоставления по времени. Пороги SLA по CPU и памяти к ним
  не применяй: они проверяются по своим запросам в доменах узлов и JVM, и «Провал» из-за aux_resources не ставь.
- Суммарный RPS сервисов не сравнивай с target_rps: целевой RPS проверен программно (sla_step).
