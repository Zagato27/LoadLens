ЗАДАЧА: анализ ERROR-логов приложений из OpenSearch в ходе нагрузочного теста.

ДАННЫЕ ДОМЕНА:
- intervals[] — агрегированные ошибки по интервалам времени; интервал агрегации совпадает с resample_interval метрик.
- Имя сервиса — в поле hostname; тип ошибки построен из нормализованного message (идентификаторы, UUID и длинные
  числа заменены плейсхолдерами); samples — примеры исходных сообщений только для иллюстрации типа.
- Признак truncated/max_documents — данные обрезаны, картина может быть неполной.

ФОКУС АНАЛИЗА:
1. Были ли значимые всплески ошибок и в какие интервалы; сопоставь интервалы с load_steps (по времени), чтобы указать,
   на какой ступени нагрузки ошибки появились или выросли.
2. Какие hostname дали основной вклад и какие нормализованные типы ошибок преобладают — группируй по типу, а не по
   уникальным сообщениям.
3. Характер ошибок по тексту типа: таймауты, отказ зависимости, ошибки данных, единичный шум. Не придумывай причины,
   которых нет в message/samples.
4. Если ошибок нет или их слишком мало для вывода — одна находка со severity=low об отсутствии значимых ошибок либо
   verdict="Недостаточно данных" с объяснением.

ТРЕБОВАНИЯ К ДОКАЗАТЕЛЬСТВАМ:
- В каждой находке: hostname (component), интервал времени, количество ошибок (count) и нормализованный тип ошибки.
- Не делай выводов по одному sample_message без агрегированного count.
- Если данные обрезаны по max_documents — снизь confidence и укажи риск неполной картины в evidence_summary.
- metric в evidence_items — "application_logs.error_count", threshold — "не задан", если порога ошибок нет в SLA.
