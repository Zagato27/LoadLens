ОБЩИЕ РЕКОМЕНДАЦИИ ПО SLA (по мировой практике):
1. JVM-метрики:
   - Использование Heap: < 75% от максимума
   - Время на GC: < 5% CPU времени
   - Паузы GC: < 200 мс
   - Использование CPU: < 70%

2. Database-метрики:
   - Время выполнения запросов: P95 < 100 мс
   - Доступность: 99.9%
   - Производительность: Apdex ≥ 0.85

3. Kafka-метрики:
   - Задержка: < 10 мс
   - Lag консьюмерских групп: < 1000 сообщений
   - Доступность: 99.95%

4. Микросервисы:
   - Время отклика: P95 < 2000 мс
   - Apdex: ≥ 0.85
   - Частота ошибок: < 0.1%
   - Доступность: 99.9%

5. Общесистемные показатели:
   - Целевое время отклика для E2E транзакций: P95 < 500 мс
   - Целевая доступность системы: 99.9%
   - Максимальное время восстановления после сбоя: < 5 минут

6. Метрики lt_framework (инструмент нагрузочного тестирования):
   - Время отклика (latency P95): норма < 2000 мс; предупреждение 2000–5000 мс; критично > 5000 мс.
   - Проверки в секунду (checks/s): норма < 10; предупреждение 10–50; критично > 50.
   - Стабильность генератора: отсутствие систематических провалов RPS при неизменной целевой нагрузке; минимальные очереди/ретраи.
   - Если test_profile.mode="stability", это тест стабильности, а не поиск максимума:
     НЕ рассчитывайте peak_performance, НЕ делайте вывод о максимальном RPS.
     Оценивайте удержание нагрузки, просадки RPS, latency, errors/checks, ресурсные тренды и накопление деградации.
   - Пиковая производительность применима только если designated_peak_performance.not_applicable не true.
     ИСПОЛЬЗУЙТЕ ТОЛЬКО поле designated_peak_performance из контекста.
     Это единственный авторитетный источник max_rps.
     НЕ ИСПОЛЬЗУЙТЕ RPS из домена microservices для определения максимальной производительности.
     Кратковременные пики — НЕ являются максимальной производительностью.
     Метод: "last_stable_step".
   - Если в контексте есть поле deterministic_sla, считайте его авторитетным результатом детерминированной проверки SLA.
     НЕ пересчитывайте достижение target_rps самостоятельно по тексту доменных отчетов.
     Формулировку о достижении/недостижении целевого RPS берите только из deterministic_sla.target_rps_check.

ТРЕБОВАНИЯ К АНАЛИЗУ:
1. Синтезировать целостный отчет на основе готовых аналитических результатов:
   - Извлечь и обобщить ключевые метрики из каждого отчета
   - Сопоставить одинаковые временные интервалы между разными компонентами
   - Определить общесистемные тенденции и закономерности
   - Оценить соответствие всей системы рекомендуемым SLA

2. Произвести комплексный кросс-компонентный анализ:
   - Выявить причинно-следственные связи между компонентами
   - Определить, как проблемы в одном компоненте влияют на другие
   - Найти общие точки отказа и критические зависимости
   - Выделить каскадные эффекты при деградации отдельных компонентов
   - Учитывать известную архитектуру, критичные потоки и зависимости из контекста системы, если они заданы

3. Выявить и описать:
   - Системные узкие места на основе имеющихся данных
   - Межкомпонентные взаимодействия, влияющие на производительность
   - Приоритетные направления оптимизации системы в целом
   - Для capacity/step тестов: максимальную устойчивую производительность системы — ТОЛЬКО из designated_peak_performance
     (НЕ из домена microservices, только lt_framework stable_max)
   - Для stability/soak тестов: стабильность под нагрузкой — по deterministic_sla и временным трендам доменов, без peak_performance.

ТРЕБОВАНИЯ К НАСЫЩЕННОСТИ И ФОРМАТУ (ВСЕ ТЕКСТОВЫЕ ПОЛЯ — НА РУССКОМ):
- Минимум 5 пунктов в findings и 5 в recommended_actions (если достаточно данных).
- Для каждого findings укажите фиксированные поля: id, summary, severity (critical/high/medium/low), component, start_time, end_time, peak_time, evidence_summary, evidence_items[].
- Каждый элемент evidence_items должен быть объектом {metric, observed_value, threshold, note}.
- id у findings должен быть коротким ASCII-идентификатором вроде f1, f2.
- Каждый элемент recommended_actions должен быть объектом {summary, details, priority, affected_components[], for_finding_ids[]}, где for_finding_ids ссылается на один или несколько id из findings.
- Поле details обязательно: 2-4 содержательных предложения о том, что именно делать, почему это должно помочь и как проверить эффект после изменения.
- Отвечайте СТРОГО в JSON: {verdict, verdict_rationale, confidence, findings[], recommended_actions[], affected_components[], peak_performance?, stability_under_load?}.
- Поле verdict ДОЛЖНО принимать только одно из значений: "Успешно" | "Есть риски" | "Провал" | "Недостаточно данных".
- Если в контексте есть deterministic_sla.verdict, итоговый verdict НЕ должен ему противоречить.
- Если deterministic_sla.target_rps_check.passed=true, нельзя писать, что система не достигла target_rps.
- Если deterministic_sla.target_rps_check.passed=false, нельзя писать, что система достигла target_rps.
- Если deterministic_sla.target_rps_check отсутствует из-за test_profile.mode="stability", не формулируйте достижение/недостижение максимальной производительности.
- Поле verdict_rationale ДОЛЖНО кратко объяснять, почему вынесен именно этот verdict: сначала 1-2 предложения с итогом, затем 2-4 ключевых фактора списком. Не дублируйте findings буквально.
- Если данных недостаточно — верните verdict="Недостаточно данных" и объясните причину в findings.

СТРУКТУРА НАРРАТИВА (для внутренней логики, но ответ — JSON):
1. Итоговый обзор нагрузки
   • Обобщение общесистемной нагрузки на основе данных по всем компонентам
   • Согласованная картина изменений нагрузки в течение теста
   • Выявление и анализ системных пиков нагрузки
   • Общая оценка соответствия SLA на уровне всей системы

2. Кросс-компонентный анализ
   • JVM-метрики и их влияние на другие компоненты
   • Database-метрики и их взаимосвязь с общей производительностью
   • Kafka-метрики и их роль в общей картине нагрузки
   • Микросервисы и их взаимодействие с другими компонентами
   • Хард-ресурсы (CPU/MEM/Disk) и их влияние на компоненты

3. Анализ каскадных эффектов и взаимозависимостей
   • Цепочки зависимостей, обнаруженные при анализе отчетов
   • Совпадающие по времени события в разных компонентах
   • Распространение деградации производительности между компонентами

4. Оценка масштабируемости и устойчивости
   • Прогноз поведения системы при увеличении нагрузки
   • Компоненты, ограничивающие масштабируемость
   • Резервы производительности в различных компонентах

5. Соответствие SLA
   • Сравнение фактических показателей с рекомендуемыми SLA
   • Компоненты, не соответствующие рекомендуемым SLA
   • Влияние отклонений на общесистемную производительность
   • Укажите максимальную достигнутую производительность (если доступно), как max_rps и момент времени, метод расчета: max_step_before_drop

6. Заключение и рекомендации
   • Приоритизированный список системных узких мест
   • Рекомендации по оптимизации с учетом взаимозависимостей
   • Предложения по улучшению общесистемного мониторинга
   • Итоговая оценка соответствия системы рекомендуемым SLA

ВАЖНО:
1. Сосредоточьтесь на связях и взаимодействиях между компонентами
2. Выделяйте временные корреляции между разными компонентами
3. Особое внимание уделите сквозной производительности
4. Приоритизируйте рекомендации на основе системного воздействия, а не локальных улучшений
5. Обязательно сравнивайте фактические показатели с рекомендуемыми SLA
6. НЕ ПРИДУМЫВАТЬ ДАННЫХ. Если в исходных отчетах что-то не указано, отметить это как пробел в данных.
7. НЕ ДЕЛАТЬ ПРЕДПОЛОЖЕНИЙ о причинах и следствиях, если они не очевидны из числовых данных.
8. НЕ ВВОДИТЬ НОВЫХ ТЕРМИНОВ или метрик, которых нет в исходных отчетах.
9. При невозможности сделать вывод из-за недостаточности данных — честно указать на это.
10. Использовать только те числовые значения, которые явно приведены в исходных отчетах.
