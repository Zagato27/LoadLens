# Запуск тестов из LoadLens

Страница «Запуск теста» (`/launch`) запускает нагрузочные инструменты на генераторах нагрузки, следит за ними, показывает базовые метрики и по завершении сама строит отчёт за окно прогона. LoadLens не заменяет инструменты и не меняет скрипты: он собирает команду из шаблона инструмента и параметров, которые ввёл инженер, и выполняет её на генераторе по SSH, в контейнере Docker или в Job Kubernetes, а пайплайн GitLab CI или задачу Jenkins запускает как есть, с выбранными веткой и параметрами пайплайна.

## Как это устроено

Прогон — это один или несколько инстансов, запущенных вместе: например, REST-сценарий в k6 и Kafka-сценарий в Gatling при комплексном тестировании. Каждый инстанс — процесс инструмента на генераторе. Инстансы одного прогона могут работать на разных генераторах, в разных инструментах и даже на генераторах разных типов.

1. Инженер выбирает сервис, тип теста и добавляет инстансы: генератор, инструмент, скрипт, параметры запуска, переменные окружения и задержку старта.
2. LoadLens проверяет форму, собирает команды и сохраняет прогон в таблицу `load_test_runs`.
3. Фоновый наблюдатель запускает инстансы, раз в несколько секунд опрашивает их, отправляет команды остановки и отмечает время начала и конца.
4. Когда последний инстанс завершился, LoadLens ждёт, пока метрики дойдут до хранилища, и запускает отчёт за окно от первого старта до последнего завершения.

Тип теста из формы определяет программный анализ отчёта, как на странице «Новый отчёт». Профиль нагрузки остаётся в скрипте.

## Генераторы нагрузки

Генераторы настраивает администратор: «Настройки → Подключения → Генераторы нагрузки» или раздел `load_generators` в `settings.py`.

Новый генератор добавляется мастером из четырёх шагов:

1. **Тип и название.** Название видят инженеры в форме запуска. Служебный идентификатор LoadLens назначает сам по типу (`gen`, `docker-2`, `k8s` и так далее), он виден в сводке карточки и нужен только для API и конфигурации.
2. **Подключение.** Адрес и учётные данные, кнопка «Проверить подключение». Для SSH проверка обязательна: она показывает отпечаток ключа сервера, и дальше мастер пускает только после подтверждения «Доверяю этому ключу». Остальные типы можно сохранить без проверки, тогда генератор отмечен как непроверенный.
3. **Инструменты и каталоги.** Проверка заполняет список инструментов: на SSH — найденные на генераторе с версиями, в Docker — те, чьи образы есть на хосте; у остальных подписано, чего не хватает. После правки каталогов можно проверить ещё раз.
4. **Лимиты и сохранение.** Число инстансов одновременно, переменные окружения генератора и итог проверки. Кнопка «Сохранить генератор» сохраняет только новый генератор, другие несохранённые правки раздела остаются в форме.

Существующий генератор правится в карточке. Кнопка «Проверить» у карточки проверяет подключение по данным формы, ещё до сохранения, и для незакреплённого ключа SSH тоже спрашивает подтверждение.

Успешная проверка записывает в генератор отметку `verified` (время и адрес, к которому подключались). Отметка действует, пока не меняются данные подключения: адрес, порт, пользователь, пространство имён, проект или задача CI. Правка каталогов, инструментов и лимитов её не сбрасывает. Карточка показывает «проверен» с датой или «не проверен», а форма запуска помечает непроверенные генераторы, но запуск на них не запрещает.

| Тип | Как LoadLens запускает инстанс | Остановка | Лимит длительности |
|---|---|---|---|
| SSH | процесс в фоне под GNU `timeout`, состояние — в файлах каталога инстанса | сигнал или команда инструмента, затем `SIGKILL` группы процессов | `timeout` на генераторе |
| Docker | контейнер через Docker Engine API | сигнал контейнеру или команда инструмента через exec | наблюдатель LoadLens |
| Kubernetes | Job с `backoffLimit: 0` | удаление пода с grace-периодом (SIGTERM, затем SIGKILL) | `activeDeadlineSeconds` |
| GitLab CI | пайплайн проекта с выбранными веткой и параметрами | отмена пайплайна (нужен API-токен) | лимит задачи CI; после лимита прогона наблюдатель отменяет пайплайн |
| Jenkins | сборка задачи с выбранными параметрами | остановка сборки | лимит задачи; после лимита прогона наблюдатель останавливает сборку |
| Вручную | ничего не запускает, отмечает окно кнопками | кнопка «Завершить» | — |

Общие поля всех типов: `title`, `tools` (какие инструменты доступны и их пути или образы; пусто — все), `max_parallel` (инстансов на генераторе одновременно, 0 — без лимита), `env` (переменные для всех инструментов на генераторе), `scripts_dir`.

### SSH

```python
"gen-1": {
    "title": "Генератор 1", "type": "ssh",
    "ssh": {"host": "10.0.0.5", "port": 22, "username": "loadlens",
            "private_key": "-----BEGIN OPENSSH PRIVATE KEY-----\n...",  # или "password"
            "passphrase": "", "host_key": "ssh-ed25519 AAAA..."},       # ключ хоста закрепляет «Проверить»
    "work_dir": "/opt/loadlens/runs",      # каталоги инстансов
    "scripts_dir": "/opt/loadlens/tests",  # относительные пути скриптов и поиск в форме
    "tools": {"k6": {}, "jmeter": {"executable": "/opt/jmeter/bin/jmeter"},
              "gatling": {"executable": "/opt/gatling/bin/gatling.sh", "scripts_dir": "/opt/gatling/user-files/simulations"}},
}
```

Нужны Linux с POSIX `sh`, GNU `timeout`, `nohup` и установленные инструменты; заведите для LoadLens отдельного пользователя с правом записи в `work_dir`. При первой проверке LoadLens показывает отпечаток ключа сервера и просит подтвердить доверие: сверьте его с ключом на самом сервере (`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`). Подтверждённый ключ закрепляется после сохранения; без закреплённого ключа LoadLens не подключится. Если ключ сервера изменился, проверка и запуск отказывают с обоими отпечатками: очистите поле и проверьте снова, только если сервер действительно переустановлен.

На генераторе у инстанса свой каталог `<work_dir>/<run_id>/<NN-тег>/` (права 0700) с `output.log`, `exit_code`, `started_at`, `finished_at` и `pid`. Скрипт запуска `runner.sh` хранит значения переменных окружения инстанса, поэтому создаётся с правами 0600 и удаляет себя, как только инструмент запущен; переменные экспортируются внутри него и не видны в списке процессов. Остальные файлы LoadLens не удаляет: чистите `work_dir` по расписанию.

### Docker

```python
"docker-1": {
    "title": "Docker на gen2", "type": "docker",
    "docker": {"url": "https://gen2.example.ru:2376", "ca_cert": "-----BEGIN CERTIFICATE-----...",
               "client_cert": "-----BEGIN CERTIFICATE-----...", "client_key": "-----BEGIN PRIVATE KEY-----...", "verify": True},
    "network": "loadtest",                                    # сеть контейнеров
    "mounts": [{"source": "loadlens-scripts", "target": "/scripts", "read_only": True}],  # том или путь на хосте
    "scripts_dir": "/scripts", "work_dir": "/tmp",            # пути внутри контейнера
    "resources": {"cpus": 2, "memory_mb": 2048},
    "remove_finished": True,                                  # удалить контейнер, журнал остаётся в прогоне
    "tools": {"k6": {}, "locust": {}, "jmeter": {"image": "justb4/jmeter:5.5"}},
}
```

LoadLens работает с Docker Engine API по HTTPS с клиентскими сертификатами (`dockerd --tlsverify`) или через фильтрующий прокси перед `/var/run/docker.sock`, например `tecnativa/docker-socket-proxy` с `CONTAINERS=1 IMAGES=1 EXEC=1 NETWORKS=1 VOLUMES=1 POST=1`. Локальный сокет напрямую не поддерживается. Образ инструмента берётся из настроек генератора или из шаблона (по умолчанию `grafana/k6:0.54.0` и `locustio/locust:2.31.8`; для JMeter и Gatling образ задаёт администратор) и должен заранее лежать на Docker-хосте: проверка генератора покажет, каких образов нет. Контейнер называется по прогону и инстансу, повторный запуск находит существующий. В Docker нет своего лимита времени: контейнер, работающий дольше предельной длительности прогона, останавливает наблюдатель LoadLens.

### Kubernetes

```python
"k8s-perf": {
    "title": "Кластер нагрузки", "type": "kubernetes",
    "kubernetes": {"api_url": "https://k8s.example.ru:6443", "token": "eyJ...", "ca_cert": "-----BEGIN CERTIFICATE-----..."},
    # или "kubernetes": {"in_cluster": True} — LoadLens работает в этом кластере под своим сервисным аккаунтом
    "namespace": "loadtest",
    "scripts": {"config_map": "loadtest-scripts"},            # или {"pvc": "scripts"}; без них — скрипты в образе
    "scripts_dir": "/scripts",
    "resources": {"cpu": "2", "memory": "2Gi"}, "node_selector": {"role": "loadgen"},
    "service_account": "", "image_pull_secret": "", "ttl_seconds": 3600,
}
```

Сервисному аккаунту LoadLens нужна Role в пространстве имён: `jobs` — create, get, list, delete; `secrets` — create, delete; `pods` — list, get, deletecollection; `pods/log` — get; `configmaps` — get, если скрипты в ConfigMap. Проверка генератора спрашивает эти права через SelfSubjectAccessReview и перечисляет недостающие. Переменные окружения инстанса уходят в Secret, которым владеет Job, а не в спецификацию Job. Под не получает токен сервисного аккаунта и не может повышать привилегии. Ошибка образа (`ImagePullBackOff` и подобные) через три минуты переводит инстанс в «Ошибка» с причиной; завершившиеся Job удаляет `ttlSecondsAfterFinished`.

### GitLab CI и Jenkins

Для CI-генератора LoadLens запускает пайплайн команды как есть: инструмент, скрипт, флаги и окружение задаёт сам пайплайн. У такого инстанса в форме запуска выбираются ветка и значения параметров пайплайна, которые LoadLens читает из GitLab или Jenkins; запуск, статус, журнал и отмена идут через API CI.

```python
"gitlab": {
    "title": "GitLab", "type": "gitlab",
    "gitlab": {"url": "https://gitlab.example.ru", "project": "perf/load-tests", "ref": "",  # "" — ветка проекта по умолчанию
               "api_token": "glpat-...", "inputs": "auto"},      # scope api: параметры, запуск, статус, отмена
    "loadlens_url": "https://loadlens.example.ru",                  # необязательно: события пайплайна
    "tags_metrics": True,                                          # пайплайн передаёт LOADLENS_RUN_TAG инструменту
},
"jenkins": {
    "title": "Jenkins", "type": "jenkins",
    "jenkins": {"url": "https://jenkins.example.ru", "job": "perf/load-test", "ref": "",  # ветка multibranch-задачи
                "username": "loadlens", "api_token": "11ab..."},
    "param_options": {"STAND": ["stage", "preprod"]},              # варианты, которые Jenkins не отдаёт
}
```

**Какие параметры видит форма.**

- **GitLab:** переменные верхнего уровня с `description`, как в форме GitLab «Run pipeline»; их `options` становятся выбором. Входные параметры `spec:inputs` из заголовка конфигурации приходят с типами, вариантами и обязательностью. Переменные LoadLens читает через GraphQL (`ciConfigVariables`; на старых версиях по `sha` и без вариантов), если GraphQL их не отдаёт — из слитой конфигурации CI lint, затем из самого `.gitlab-ci.yml`. Входные параметры всегда читаются из файла конфигурации.
- **Jenkins:** параметры задачи — строка, текст, флаг, выбор, пароль. У Active Choices варианты считает скрипт на странице сборки: если скрипт просто возвращает список (`return ['stage', 'preprod']`), LoadLens читает его из `config.xml` (нужно право Job/ExtendedRead), иначе поле остаётся текстовым, а варианты можно задать в `param_options` генератора. Файловые параметры не поддерживаются. У pipeline-задачи параметры из Jenkinsfile появляются после первой сборки. У multibranch-задачи ветка выбирается при запуске.
- Параметры `LOADLENS_*` (у входных параметров GitLab — `loadlens_*`) форма не показывает: их заполняет LoadLens. Список параметров кэшируется на минуту; кнопка «Обновить параметры» в инстансе читает его заново.

**Что уходит в CI.** Только значения, которые отличаются от значений по умолчанию в пайплайне; пустой пароль оставляет секрет из CI. GitLab получает переменные пайплайна и, если версия это умеет, входные параметры: режим `inputs` — `auto` (с GitLab 17.11), `on` или `off`; на версиях без поддержки входные параметры только показываются, и пайплайн берёт их значения по умолчанию. Дополнительные переменные GitLab задаются в форме строками `ИМЯ=значение`. Если проект запрещает переменные пайплайна (так по умолчанию у новых проектов GitLab 17.7+), LoadLens запускает пайплайн без `LOADLENS_*` и пишет об этом в инстансе; свои значения тогда передавайте входными параметрами. Jenkins получает выбранные значения и объявленные в задаче параметры `LOADLENS_*`; задача без параметров запускается обычной сборкой.

Переменные `LOADLENS_*`: `LOADLENS_RUN_ID`, `LOADLENS_RUN_NAME`, `LOADLENS_RUN_TAG`, `LOADLENS_INSTANCE`, `LOADLENS_INSTANCE_INDEX`, `LOADLENS_MAX_SECONDS`, а при заданном `loadlens_url` ещё `LOADLENS_EVENTS_URL` и `LOADLENS_TOKEN`. Пайплайну они не обязательны; два полезных приёма:

```yaml
# .gitlab-ci.yml: тег прогона в метриках k6 (у генератора включите tags_metrics)
load-test:
  script:
    - k6 run --tag testid="${LOADLENS_RUN_TAG:-manual}" --out experimental-prometheus-rw k6/load.js
```

```sh
# точное окно теста: события started и finished, если у генератора задан loadlens_url
post() { [ -n "$LOADLENS_EVENTS_URL" ] && curl -fsS -m 10 -H "X-LoadLens-Token: $LOADLENS_TOKEN" \
  -H "Content-Type: application/json" -d "$1" "$LOADLENS_EVENTS_URL" > /dev/null || true; }
post '{"event":"started"}'
code=0; k6 run k6/load.js || code=$?
post "{\"event\":\"finished\",\"exit_code\":$code}"
exit $code
```

**Статус и окно отчёта.** Начало и конец инстанса LoadLens берёт из CI — время пайплайна GitLab или сборки Jenkins, а если пайплайн прислал события, то из них. Время пайплайна включает подготовку (скачивание образа, сборку), поэтому окно отчёта прогона с CI-инстансами сужается по данным: от первой до последней точки, где суммарный RPS выше нуля, плюс шаг запроса с каждой стороны; паузы внутри теста остаются. Если данных RPS нет, отчёт берёт время пайплайна и пишет об этом в сообщении прогона. На странице прогона у инстанса есть ссылка на пайплайн или сборку.

**Остановка** отменяет пайплайн GitLab (нужен API-токен) или останавливает сборку Jenkins. Без API-токена GitLab LoadLens не видит параметры, статус и журнал пайплайна и не может его отменить: значения задаются дополнительными переменными, а окно закрывается событием пайплайна, кнопкой «Остановить» (через `grace_seconds`, с просьбой отменить пайплайн вручную) или по лимиту длительности; отчёт и тогда сужается по RPS.

**Права.** GitLab — токен со scope `api` и ролью Developer в проекте; `read_api` хватает только для чтения параметров. Jenkins — пользователь с Job/Read, Job/Build, Job/Cancel и, для Active Choices, Job/ExtendedRead.

## Шаблоны инструментов

Встроенные шаблоны: k6, JMeter, Locust, Gatling (бандл до 3.10) и Gatling (Maven, в том числе бандлы 3.11+). Администратор меняет их в «Настройки → Подключения → Инструменты НТ» или в разделе `load_tools`; сохраняются только отличия от встроенных шаблонов, поэтому их исправления в новых версиях продолжают действовать. Можно добавить свой инструмент, например Яндекс.Танк.

| Ключ | Назначение |
|---|---|
| `command` | Команда с подстановками. `{params}` — параметры из формы, отдельным словом |
| `executable` | Что подставляется вместо `{exe}`; генератор может задать свой путь |
| `image` | Образ для Docker и Kubernetes |
| `env` | Переменные окружения. Значение из формы с тем же именем дописывается через пробел, что удобно для `JAVA_OPTS` |
| `cwd` | Рабочий каталог процесса, по умолчанию каталог скрипта |
| `script_kind` | `file` — путь к файлу, `class` — класс симуляции Gatling, `none` — без скрипта |
| `scripts_glob` | Маски, по которым форма ищет скрипты на генераторе |
| `success_exit_codes` | Коды успешного завершения |
| `failed_checks_exit_codes` | Коды «процесс отработал, пороги не пройдены»: k6 `99`, Gatling `2`, Locust `1`. Отчёт строится и в этом случае |
| `stop_signal`, `grace_seconds` | Сигнал остановки и сколько ждать перед `SIGKILL` |
| `stop_command` | Мягкая остановка командой самого инструмента вместо сигнала (SSH и Docker); при ошибке уходит сигнал |
| `status_command` | Команда статуса, раз в 15 секунд, ответ показывается у инстанса |
| `version_command` | Команда версии для проверки генератора |
| `run_filter_packs` | Пакеты запросов, которые видят тег прогона, см. ниже |

Подстановки: `{exe}`, `{exe_dir}` (каталог исполняемого файла со слешем на конце или пусто), `{script}`, `{script_dir}`, `{scripts_dir}`, `{run_name}`, `{run_tag}`, `{instance}`, `{instance_tag}`, `{instance_dir}`, `{control_port}` (порт управления инстанса, свой у каждого инстанса), `{params}`.

Шаблон сначала делится на слова, затем в каждое слово подставляются значения, поэтому значение никогда не превращается в несколько аргументов. Параметры из формы делятся на слова по правилам оболочки: кавычки группируют, а `$`, `;`, обратные кавычки и подстановки команд не раскрываются. Каждый аргумент передаётся на генератор в одинарных кавычках.

Встроенные команды:

```text
k6:      {exe} run --address 127.0.0.1:{control_port} --tag testid={run_tag} --tag lt_instance={instance_tag} {params} {script}
         статус: {exe} status --address 127.0.0.1:{control_port}   (у инстанса видно «VU 12 из 20»)
JMeter:  {exe} -n -t {script} -j {instance_dir}/jmeter.log -Japplication={run_tag} -Jlt_instance={instance_tag}
            -Jjmeterengine.nongui.port={control_port} -Jjmeterengine.nongui.maxport={control_port} {params}
         мягкая остановка: {exe_dir}shutdown.sh {control_port}   (сэмплеры доработают, Backend Listener допишет последнюю пачку)
Locust:  {exe} -f {script} --headless {params}
Gatling: {exe} -rm local -s {script} -rd {run_tag} {params}
Maven:   {exe} gatling:test -Dgatling.simulationClass={script} {params}
```

## Прогон и его инстансы

Статусы инстанса: ожидает старта, запускается, идёт, завершён, завершён с непройденными порогами, ошибка, остановлен, остановлен по лимиту длительности, потерян, отменён. Статусы прогона: запускается, идёт, останавливается, ждёт метрики, строится отчёт, завершён, не запустился, отменён.

- **Задержка старта** откладывает запуск инстанса относительно создания прогона.
- **Остановка.** «Остановить» у инстанса или «Остановить прогон» запускает мягкую остановку инструмента, если она есть, иначе сигнал из шаблона; не завершившийся за `grace_seconds` процесс получает `SIGKILL`. В Kubernetes остановка удаляет под с grace-периодом, в CI — отменяет пайплайн. Если генератор не подтвердил остановку через две минуты после `SIGKILL` или не принимает её вовсе, LoadLens закрывает окно инстанса с пометкой проверить процесс вручную, чтобы прогон, его слоты и отчёт не ждали вечно.
- **Предельная длительность** задаётся в форме и ограничена лимитом `max_load_test_hours`. Инстанс, который не стартовал за это время, считается неудачным. Docker и ручной режим ограничивает наблюдатель; генераторы со своим таймером (SSH, Kubernetes, CI) он останавливает сам, если через две минуты после лимита инстанс ещё идёт. Окно ручного инстанса закрывается по лимиту.
- **Журнал.** Хвост вывода инструмента виден на странице прогона; когда инстанс завершается, последние 32 КБ сохраняются в прогоне, поэтому журнал доступен и после удаления контейнера или Job.
- **Рестарт LoadLens.** Процессы, контейнеры и Job не зависят от LoadLens. После перезапуска наблюдатель подхватывает идущие прогоны; если работает несколько процессов LoadLens, прогоны замолчавшего наблюдателя через две минуты забирает другой. Наблюдатель продлевает захват прогона во время долгого прохода и записывает секрет CI-инстанса до запуска пайплайна.
- **Окно отчёта** — от первого старта до последнего завершения. Инстанс, упавший в первую минуту, в окно не входит; если ни один инстанс не запустился, прогон завершается без отчёта.

Несколько прогонов на одном генераторе разрешены: форма предупреждает, что там уже идёт прогон, но не запрещает. Жёсткий предел задаёт `max_parallel` генератора.

## Пресеты, повтор и подсказки вывода

- **Пресет** — сохранённая форма запуска сервиса (инстансы, параметры, тип теста, длительность, настройки отчёта), общая для инженеров. Значения переменных окружения в пресет не попадают: остаются только имена, значения вводятся при запуске. Одноимённый пресет перезаписывает и удаляет его автор или администратор; остальным форма предлагает сохранить под другим названием.
- **«Повторить»** на странице прогона и «Повторить запуск» в меню архива для прогонов с меткой «запущен из LoadLens» открывают форму с инстансами и параметрами прошлого прогона; форма называет переменные окружения, значения которых нужно ввести заново.
- **«Вывод метрик»** у инстанса добавляет в параметры и переменные флаги вывода метрик под источник домена «Нагрузка» сервиса и установленные пакеты: remote write k6 для Prometheus и VictoriaMetrics, вывод в InfluxDB для InfluxQL через Grafana, Graphite-вывод Gatling. Адреса подставляются так, как их видит LoadLens, — с генератора они могут быть другими; учётные данные источника в подсказку не попадают.

## Как метрики прогона отделяются от других тестов

Из имени прогона получается тег из латиницы, цифр, `_` и `-`, например `release-2-5-step`. Инструменты, которые умеют помечать метрики, получают его в команде, а отчёт и живые графики подставляют его в переменную пакета запросов (`[run_filter]` в TOML пакета).

| Инструмент | Как помечается | Пакеты |
|---|---|---|
| k6 | `--tag testid=<тег>` во все выводы | `lt-k6-prometheus-rw`, `lt-k6-prometheus-native`, `lt-k6-influxql` |
| JMeter | `-Japplication=<тег>`, если Backend Listener читает `${__P(application,…)}` | `lt-jmeter-influxql` |
| Gatling | не помечается по умолчанию; тегом можно заменить префикс Graphite или имя симуляции (ниже) | `lt-gatling-graphite-victoriametrics`, `lt-gatling-graphite-victoriametrics-labels` |
| Locust | не помечается | отделяется окном прогона |
| Пайплайн CI | своей командой из `LOADLENS_RUN_TAG`, у генератора включён `tags_metrics` | установленные пакеты с фильтром прогона |

Если запрос с тегом ничего не нашёл, а без тега данные есть, инструмент не пометил метрики — так бывает у тест-плана JMeter с фиксированным `application`. Тогда отчёт и графики читают все метрики окна и пишут об этом в сообщении прогона. Метрики инструментов без тега, которые одновременно писали в то же хранилище, попадут в отчёт; форма предупреждает об этом, если в прогоне несколько инстансов. Если в прогоне есть CI-инстанс без `tags_metrics`, фильтр по тегу для всего прогона выключается: иначе он спрятал бы метрики пайплайна.

**Gatling в VictoriaMetrics с тегом.** Префикс Graphite можно заменить тегом прогона: в шаблоне `gatling` задайте `"env": {"JAVA_OPTS": "-Dgatling.data.graphite.rootPathPrefix={run_tag}"}` и `"run_filter_packs": ["lt-gatling-graphite-victoriametrics"]`. Для InfluxDB с graphite-шаблоном `gatling.*` так делать нельзя: метрики с другим префиксом не пройдут шаблон.

**Gatling в VictoriaMetrics с relabeling.** Если VictoriaMetrics переименовывает пути Graphite в ряды с метками, ставьте пакет `lt-gatling-graphite-victoriametrics-labels`. Он ждёт такие правила `-relabelConfig` (они же — `docker/dev-stack/gatling/vm-relabel.yml`):

```yaml
# Пользователи: gatling.<симуляция>.users.<сценарий|allUsers>.<active|waiting|done>. Правило — первым:
# эти пути тоже из пяти частей и иначе попадут под правило запросов.
- action: graphite
  match: 'gatling.*.users.*.*'
  labels:
    __name__: 'gatling_users_${3}'
    simulation: '$1'
    request: '$2'
# Запросы в группе: gatling.<симуляция>.<группа>.<запрос>.<статус>.<метрика>
- action: graphite
  match: 'gatling.*.*.*.*.*'
  labels:
    __name__: 'gatling_request_${5}'
    simulation: '$1'
    request: '${2}.${3}'
    status: '$4'
# Запросы и сводка allRequests: gatling.<симуляция>.<запрос>.<ok|ko|all>.<count|mean|percentiles95|…>
- action: graphite
  match: 'gatling.*.*.*.*'
  labels:
    __name__: 'gatling_request_${4}'
    simulation: '$1'
    request: '$2'
    status: '$3'
```

В `match` каждая `*` — одна часть пути без точек, `$N` — N-я звёздочка. Частая ошибка — правило `gatling.users.*.*.*`: Gatling пишет пользователей после имени симуляции, поэтому оно не срабатывает, и пользователи попадают под правило запросов как `gatling_request_active{request="users", status="allUsers"}`. Пакет читает и такой ряд. Без правила для групп запросы внутри `group(...)` остаются путями Graphite и не видны в разбивке по запросам; общие цифры `allRequests` это не задевает. Вложенные группы дают пути длиннее шести частей: на каждый уровень нужно своё правило.

Тег прогона здесь подставляется вместо имени симуляции, а не префикса: префикс `gatling` нужен правилам. В шаблоне `gatling` задайте `"env": {"JAVA_OPTS": "-Dgatling.core.outputDirectoryBaseName={run_tag}"}` и `"run_filter_packs": ["lt-gatling-graphite-victoriametrics-labels"]`: Gatling пишет тег в путь Graphite вместо имени симуляции, он попадает в метку `simulation`, а пакет фильтрует по ней. Каталог результатов Gatling тоже получит имя тега. Пайплайн CI делает то же своей командой из `LOADLENS_RUN_TAG` и включённым `tags_metrics` у генератора. Проверено на бандле Gatling 3.10.5.

## Комплексный прогон и суммарный RPS

Домен «Нагрузка» читает один источник одним языком запросов, поэтому инструменты комплексного прогона пишут в одно хранилище, например k6 через remote write и Gatling через Graphite в VictoriaMetrics, а в домене установлены пакеты обоих инструментов. Ступени и SLA считаются по одному ряду — `max_performance_query`.

Кнопка «Суммарный RPS инструментов» в разделе «Запросы» (появляется, когда в домене больше одного запроса с ролью «Общий RPS теста») добавляет строку `LT: RPS total, all tools`, которая складывает общий RPS всех инструментов, и делает её запросом производительности SLA. Строка пересобирается из своих частей при каждом сохранении запросов и после фильтра прогона, поэтому в отчёте прогона сумма отфильтрована вместе с частями; живая панель тоже показывает сумму. Работает для PromQL; для InfluxQL и Flux суммы нет.

## Живые метрики и отчёт

Страница прогона показывает RPS, долю ошибок, p95 и число пользователей по запросам с ролями `lt.rps_total`, `lt.error_rate_pct`, `lt.p95_total`, `lt.vus` домена «Нагрузка» сервиса: последние значения строкой цифр и три графика — RPS с долей ошибок, p95 и пользователи. Если пакет инструмента не установлен, графики пустые, а запуск всё равно работает. Ниже — таблица инстансов с командой, статусом, ответом команды статуса, кодом выхода и журналом.

- **Обновление.** Пока тест идёт, страница раз в 5 секунд дочитывает только новые точки (с перекрытием в два шага, чтобы досчитать последнее ведро), а когда прогон завершился, перечитывает окно целиком. Над графиками — подпись «данные на 12:04:31, задержка 9 с»: время последней точки RPS в хранилище. Задержка 5–15 секунд нормальна — так метрики доходят до хранилища (k6 и JMeter отправляют их раз в 5 секунд, запросы с `rate()` сглаживают окном); если новых точек нет дольше минуты, подпись подсвечивается: метрики не доходят или инструмент перестал их писать.
- **Окно.** «Весь прогон» или последние 15, 30, 60 минут. Шаг выборки подбирается под окно: на длинном прогоне весь прогон читается крупнее, последние минуты — подробнее.
- **Инстансы.** В прогоне из нескольких инстансов график RPS показывает сумму и RPS каждого инстанса по тегу `lt_instance` (запрос с ролью `lt.rps_by_instance`: есть в пакетах k6 и JMeter; JMeter пишет тег, если Backend Listener передаёт `TAG_lt_instance=${__P(lt_instance,)}`). Эта строка нужна только живым графикам: в отчёт она не попадает. Ряды без тега или с тегом другого прогона на график не выводятся.
- **Отметки.** Вертикальные линии — старт и завершение инстансов, запрос остановки и момент, когда сработает лимит длительности; горизонтальные — пороги SLA сервиса: целевой RPS, допустимая доля ошибок и p95 (`target_rps`, `max_error_rate_pct`, `max_p95_ms`).

**На дэшборде.** Инженеры и администраторы видят идущие прогоны активной области в блоке «Идут сейчас» под строкой статуса: статус, сервис, кто запустил, сколько инстансов идёт, время против лимита и, когда нагрузка пошла, RPS за последние 15 минут со спарклайном и доля ошибок (те же роли `lt.rps_total` и `lt.error_rate_pct`). Блок обновляется раз в 15 секунд, пока прогоны идут, и раз в минуту, когда их нет; если метрик нет, вместо цифр — причина, как на странице прогона. Кнопка «Остановить» есть у своих прогонов, а у администратора — у всех; чужой прогон инженер останавливает со страницы прогона. Строка статуса показывает их число, пункт «Запуск теста» верхней панели — счётчик на всех страницах (опрос раз в 30 секунд). Ответ с цифрами кешируется на 10 секунд на прогон, чтобы несколько открытых дэшбордов не читали хранилище метрик каждый раз.

Отчёт запускается после паузы на доставку метрик: два шага выборки `default_params.step`, но не меньше 30 секунд и не больше 5 минут. Если все слоты фоновых задач заняты, отчёт ждёт свободного. Если дневной лимит анализа ИИ исчерпан, отчёт строится без анализа.

**Подсказка окна для отчёта вручную.** Если тест запускали не из LoadLens, форма «Новый отчёт» после выбора сервиса ищет его окно сама: читает запрос с ролью `lt.rps_total` домена «Нагрузка» за последние 6 часов и показывает до трёх последних отрезков с ненулевым RPS. Пауза дольше трёх шагов выборки разрывает отрезок, одиночные точки отбрасываются. К отрезкам добавляются завершённые прогоны сервиса из LoadLens; прогон, который пересекается с отрезком, даёт ему имя и точное время. Клик по подсказке подставляет начало и конец. Если источник не отвечает, форма пишет об этом строкой под полями и работает как раньше. Ответ кешируется на 60 секунд в каждом процессе.

## Ресурсы генераторов в отчёте

Необязательный домен `lt_generators` («Ресурсы генераторов нагрузки») показывает, не упёрся ли сам генератор в CPU, память, сеть или соединения: перегруженный генератор недодаёт нагрузку и добавляет задержку в измеренное время ответа. Установите пакет `lt-generators-node-exporter` с матчерами хостов генераторов (например `job="loadgen"`) — node_exporter должен работать на генераторах. Домен анализируется ИИ отдельно, а итоговый анализ учитывает его при вердикте; привязку к источнику домен получает, как остальные (`domain_sources.lt_generators` или `default`).

## Безопасность

- Запускать, останавливать и смотреть прогоны может роль «Инженер». Скрипты k6, Locust и Gatling — это произвольный код, а параметры запуска свободные, поэтому инженер фактически исполняет код на генераторе и видит то, что видит там инструмент, включая переменные окружения генератора. Генератор должен быть выделенной машиной, кластером или проектом CI, а учётная запись LoadLens на нём — без лишних прав; секреты в `env` генератора давайте только те, которые инженерам можно доверить.
- Инстанс не может переопределить переменные окружения генератора (иначе адрес вывода метрик можно было бы подменить рядом с паролем из настроек) и задать переменные, меняющие запуск оболочки и рантаймов: `PATH`, `LD_*`, `BASH_ENV`, `ENV`, `JAVA_TOOL_OPTIONS`, `NODE_OPTIONS`, `PYTHONPATH` и подобные. `JAVA_OPTS`, `HEAP`, `JVM_ARGS` и переменные самих инструментов разрешены. Скрипт должен лежать в каталоге скриптов генератора. В Kubernetes `$(ИМЯ)` в параметрах не раскрывается в значение переменной.
- **Docker API равен правам root на Docker-хосте.** Открывайте его только LoadLens: TLS с клиентскими сертификатами или фильтрующий прокси в закрытой сети. LoadLens не создаёт привилегированных контейнеров и монтирует только то, что задал администратор.
- **Kubernetes.** Role только на пространство имён нагрузки; под без токена API и без повышения привилегий; переменные инстанса — в Secret, а не в спецификации Job.
- **CI.** LoadLens запускает пайплайн токеном CI из настроек. Значения обычных параметров видны в GitLab и Jenkins участникам проекта или задачи, поэтому секреты передавайте password-параметрами Jenkins или переменными CI/CD, а не обычными параметрами. Значения password-параметров не показываются в LoadLens, стираются сразу после запуска и не попадают в пресеты и повтор. Секрет инстанса для событий хранится только в виде SHA-256 и действует, пока инстанс не завершён; эндпоинт событий не требует входа и на неверный токен отвечает так же, как на несуществующий прогон.
- Значения переменных окружения инстанса не показываются в интерфейсе и журнале действий и стираются из хранилища, когда инстанс завершился; в пресеты они не сохраняются. Токены передавайте через переменные, а не через параметры: параметры видны в команде.
- Секреты генераторов (приватный ключ и парольная фраза SSH, клиентский ключ Docker, токены Kubernetes, триггера и API CI) отдаются в настройки как `***` и подставляются, только пока адрес генератора, порт, CA, `in_cluster` и закреплённый ключ хоста SSH не менялись. После очистки ключа хоста пароль или ключ SSH нужно ввести заново: иначе проверка отправила бы их незакреплённому серверу.
- Запуск, остановка и пресеты пишутся в журнал действий (`load_test.start`, `load_test.stop`, `load_test.preset_save`, `load_test.preset_delete`) вместе с командами, в которых значения переменных скрыты.
- Лимиты: `max_parallel_load_tests` и `max_parallel_load_tests_per_user` — активные прогоны, `max_load_test_instances` — инстансы в прогоне, `max_load_test_hours` — предельная длительность.

## API

С API-токеном роли «Инженер» и выше:

- `GET /load_tests/options` — генераторы, инструменты и лимиты, без учётных данных.
- `GET /load_tests/scripts?generator=&tool=` — скрипты инструмента на генераторе (SSH, Docker, ConfigMap Kubernetes).
- `GET /load_tests/hints?service=&tool=` — флаги и переменные вывода метрик.
- `POST /load_tests/preview` — проверка формы и команды без запуска.
- `POST /load_tests` — запуск. Тело: `service`, `project_area?`, `test_type?`, `run_name?`, `max_duration_min?`, `auto_report?`, `use_llm?`, `instances: [{name, generator, tool, script, params, env, start_delay_sec}]`. Ответ: `run_id`, `run_name`, `run_tag`, `warnings`, `url`.
- `GET /load_tests/runs?active=1&limit=` — прогоны активной области; `GET /load_tests/runs/<run_id>` — прогон и инстансы, `report_url` после отчёта.
- `GET /load_tests/active?limit=5&live=1` — идущие прогоны активной области для дэшборда: `total` и до `limit` (0–20) последних прогонов со статусом, прогрессом инстансов, `can_stop` и, при `live=1`, RPS и долей ошибок за 15 минут (`live.rps`, `live.errors`, `live.points`). `limit=0` — только число.
- `POST /load_tests/runs/<run_id>/stop` — остановка прогона или инстанса (`{"index": N}`).
- `GET /load_tests/runs/<run_id>/logs?index=&bytes=` — хвост журнала инстанса; `GET /load_tests/runs/<run_id>/live?window=&since=&mode=` — живые метрики: `window` — последние 15, 30 или 60 минут (0 — весь прогон), `since` — только точки с этого момента (мс), `mode` — `filtered` или `plain` из первого ответа. Ответ: `series` по ролям, `instances` (RPS инстансов), `events`, `sla`, `fresh_at`, `step_sec`.
- `GET /lt_windows?service=&hours=6` — найденные окна теста сервиса для формы «Новый отчёт» (`hours` от 0,25 до 24). Ответ: `ok`, `windows: [{start, end, duration_sec, rps_peak, ongoing}]`, `runs` — завершённые прогоны LoadLens в том же интервале; при ошибке источника `ok: false` и `message`, HTTP-статус остаётся 200.
- `GET /load_tests/presets?service=`, `POST /load_tests/presets` (`name`, `service`, `spec` — форма запуска), `DELETE /load_tests/presets/<id>`.
- `GET /load_tests/ci_params?generator=&ref=` — параметры пайплайна CI-генератора (`params`, `ref`, `source`, `notes`, `auto`); `GET /load_tests/ci_refs?generator=&search=` — ветки проекта GitLab или multibranch-задачи Jenkins.

Без входа, по секрету инстанса в заголовке `X-LoadLens-Token` (для пайплайнов CI):

- `POST /load_tests/ci/<run_id>/<index>/events` — `{"event": "started"}` или `{"event": "finished", "exit_code": N, "message": "..."}`.

Администратор: `POST /config/query_packs/summed_rps` (`area?`, `service?`, `use_for_sla?`) — строка суммарного RPS.

```bash
curl -s -H "Authorization: Bearer $LOADLENS_TOKEN" -H "Content-Type: application/json" \
  -d '{"service":"checkout","test_type":"step","run_name":"release-2.5",
       "instances":[{"name":"rest","generator":"gen-1","tool":"k6","script":"checkout.js",
                     "params":"--out experimental-prometheus-rw",
                     "env":"K6_PROMETHEUS_RW_SERVER_URL=http://prometheus:9090/api/v1/write"}]}' \
  https://loadlens.example.ru/load_tests
```

CI-инстанс в той же форме: `{"name": "pipeline", "generator": "gitlab", "ci_ref": "main", "ci_params": {"PROFILE": "load", "users": 50}, "ci_extra": "BASE_URL=https://stage.example"}` — без `tool`, `script`, `params` и `env`.

## Неполадки

| Что видно | Причина |
|---|---|
| Код выхода 127 | Инструмент не найден: проверьте путь в генераторе или шаблоне |
| Код выхода 126, «нет рабочего каталога» | Каталог `cwd` шаблона не существует на генераторе |
| «Остановлен по лимиту длительности» | Сработала предельная длительность прогона |
| «Ключ хоста изменился» | SSH-сервер предъявил другой ключ: проверьте, что это тот же сервер, и закрепите ключ заново |
| «Ключ хоста не закреплён» | SSH-генератор сохранён без проверки: нажмите «Проверить» и сохраните |
| «Образа … нет на Docker-хосте» | Скачайте образ на Docker-хост заранее (`docker pull`) |
| «Не стартовал: ImagePullBackOff» | Kubernetes не может скачать образ: имя, тег или секрет реестра |
| «нет прав: …» в проверке Kubernetes | Role сервисного аккаунта не даёт перечисленных действий |
| Инстанс CI долго «Запускается» | Пайплайн ждёт раннер или сборка стоит в очереди: смотрите статус по ссылке «Открыть в GitLab» или «Открыть в Jenkins» |
| «Параметры пайплайна не читаются» | Проверьте API-токен (GitLab: scope api или read_api), проект или задачу и ветку; без токена задайте значения дополнительными переменными |
| «Проект GitLab запрещает переменные пайплайна» | Разрешите переменные в настройках CI/CD проекта или объявите значения входными параметрами `spec:inputs` |
| «Остановка недоступна: … API-токен» | У генератора GitLab нет API-токена для отмены пайплайна |
| «timeout не из GNU coreutils» | SSH-генератор на busybox: остановка может не дойти до дочерних процессов |
| «Процесс пропал без кода выхода» | Генератор перезагружался или процесс убили извне |
| «Метрики инструмента без тега прогона» | Инструмент не пометил метрики тегом, см. «Как метрики прогона отделяются» |
| В отчёте нет метрик инструмента | У сервиса не установлен пакет запросов инструмента или домен «Нагрузка» читает другое хранилище |

Стенд для проверки — `docker/dev-stack`: SSH-генератор с k6, Locust и бандлом Gatling, Docker через socket-proxy и заглушки GitLab и Jenkins для CI (профиль `generator`, см. его README).
