# План: очистка списка «Активные и недавние задачи»

Цель: инженер убирает из списка задач завершившиеся и оборванные записи одной кнопкой или по одной. Задачи,
которые ещё выполняются, остаются на месте. Сведения о скрытой задаче не теряются: она доступна по ссылке и в
журнале приложения.

**Статус (2026-10-13): реализовано по плану.** Уточнения:

- `POST /jobs/dismiss` возвращает списки идентификаторов `dismissed` и `skipped_running`, а не числа.
- Если последняя запись задачи в таблицу не прошла, решает состояние в памяти: завершившаяся задача скрывается.
- Проверено тестами `tests/test_jobs_dismiss.py` и прогоном в браузере на копии приложения с локальной TimescaleDB.

## 1. Что есть сейчас

| Факт | Где | Следствие |
|---|---|---|
| Список на странице «Новый отчёт» и полоса в архиве запрашивают `GET /jobs?status=running,error&limit=10` | `static/js/new.js::loadActiveJobs`, `static/js/archive.js::loadJobsStrip` | В списке только задачи «В работе» и «Ошибка». Готовые задачи туда не попадают, поэтому копятся именно ошибки |
| Задачи пишутся в таблицу `report_jobs` и в словарь процесса, удаления и скрытия нет | `loadlens_app/jobs.py::JobStore` | Ошибочная задача висит в списке, пока её не вытеснят 10 более новых |
| Задачи выполняются в потоках веб-процесса; Docker запускает один процесс gunicorn | `dashboard.py::create_report`, `forecast.py::_publish_in_background`, `docker/Dockerfile` | Если процесс перезапустился посреди задачи, её строка навсегда остаётся `running` |
| Пока в списке есть задача `running`, страницы опрашивают сервер каждые 5 секунд | `new.js`, `archive.js`, `dashboard.js::loadJobs` | Оборванная задача заставляет дэшборд, архив и «Следить» опрашивать сервер бесконечно |
| Владелец задачи хранится только в памяти процесса, в таблице его нет | `JobRecord.owner` | Отличить «мои» задачи в сохранённых строках нельзя: список общий для всех |
| Словарь задач в памяти не очищается | `JobStore._jobs` | Растёт до перезапуска. При скрытии запись из памяти не должна вернуть задачу в список |
| Подробности задачи открываются по ссылке `/new?job=<id>` через `GET /job_status/<id>` | `new.js`, `dashboard.py::job_status` | Если задачу скрывать, а не удалять, ссылки продолжают работать |

## 2. Решения

1. **Скрытие, а не удаление.** В таблице появляется колонка `dismissed_at TIMESTAMPTZ NULL`. Список не
   показывает скрытые задачи, а `GET /job_status/<id>` по-прежнему отдаёт их по ссылке. Ничего не теряется,
   а журнал действий хранит, кто и когда очистил список.
2. **Скрываются только завершившиеся задачи.** Это статусы `done` и `error`, включая оборванные из пункта 3.
   Выполняющиеся задачи сервер пропускает, даже если клиент их прислал, и сообщает, сколько пропустил.
3. **Оборванные задачи.** Строка `running`, которой нет в памяти текущего процесса и которая обновлялась раньше
   его запуска, считается оборванной. При первом обращении процесса к таблице такие строки получают статус
   `error` и сообщение «Задача прервана: сервер перезапустился во время выполнения». Это сразу останавливает
   бесконечный опрос и даёт оборванным задачам кнопку «Скрыть». Если такая задача всё же жива в другом
   экземпляре приложения, её следующее обновление прогресса вернёт статус `running`.
4. **Сервер скрывает ровно то, что видел пользователь.** «Очистить» отправляет идентификаторы видимых
   завершившихся строк, а не команду «скрыть всё». Ошибка, появившаяся после последнего обновления списка,
   не исчезнет незамеченной.
5. **Права.** Очищать могут инженер и администратор: они запускают задачи и видят список на странице
   «Новый отчёт». Наблюдатель видит полосу в архиве без кнопок. Действие пишется в журнал как `jobs.dismiss`.
6. **Без подтверждения.** Скрытие ничего не удаляет, поэтому диалог «Вы уверены?» не нужен. После очистки
   появляется уведомление «Скрыто задач: N».

## 3. Изменения по файлам

| Файл | Изменение |
|---|---|
| `loadlens_app/jobs.py` | Колонка `dismissed_at` через `ALTER TABLE … ADD COLUMN IF NOT EXISTS` в `_ensure_table`. Разовая пометка оборванных задач при первом подключении процесса. `_load_many` отбирает только строки без `dismissed_at`. `list()` не возвращает скрытые записи из памяти. Новый метод `dismiss(job_ids) -> (скрыто, пропущено)`: одним `UPDATE` с условием `status <> 'running'`, затем та же отметка в памяти. Завершившиеся задачи старше часа выгружаются из памяти: источником правды для них остаётся таблица |
| `loadlens_app/blueprints/dashboard.py` | `POST /jobs/dismiss` с телом `{"job_ids": [...]}`, не больше 100 идентификаторов. Ответ `{"dismissed": N, "skipped_running": M}`. Пустой или неверный список даёт 400, недоступная база даёт 503 |
| `loadlens_app/auth/policy.py` | Правило `"dashboard.dismiss_jobs": _write(E, "jobs.dismiss")`. Тест покрытия правил и ролевая матрица подхватят его сами |
| `templates/index.html`, `templates/archive.html` | Кнопка «Очистить завершённые» в заголовке списка с `data-min-role="engineer"`, скрыта, пока нет завершившихся строк |
| `static/js/common.js` | Общая функция `LL.dismissJobs(ids)`: запрос, уведомление, обработка ошибок |
| `static/js/new.js`, `static/js/archive.js` | Кнопка «Скрыть» в строке завершившейся задачи и кнопка «Очистить» в заголовке. После ответа список перезагружается, пустой список прячется, как сейчас |
| `static/css/app.css` | Стиль маленькой кнопки «Скрыть» в `.job-row` и кнопки в `.jobs-title` |
| `README.md` | Раздел «Новый отчёт» или «Архив»: как очистить список и что такое оборванная задача. Раздел REST API: `POST /jobs/dismiss` |

Дэшборд показывает только выполняющиеся задачи и кнопок не получает. Оборванные задачи из него уйдут сами
после пункта 3 решений.

## 4. Тесты

- `tests/test_smoke_api.py`:
  - `POST /jobs/dismiss` скрывает задачу с ошибкой, и она пропадает из `GET /jobs`;
  - `GET /job_status/<id>` скрытой задачи по-прежнему отвечает;
  - выполняющаяся задача не скрывается и попадает в `skipped_running`;
  - пустой список, не список, больше 100 идентификаторов и неизвестный идентификатор обрабатываются корректно.
- Модульные тесты `JobStore` на подменённом соединении (`RecordingConnection`, как в существующих тестах):
  - SQL скрытия содержит условие `status <> 'running'`;
  - выборка списка исключает скрытые строки;
  - строка `running` из прошлого процесса становится `error` с сообщением о прерывании;
  - задача текущего процесса не трогается;
  - скрытая запись в памяти не возвращается в список.
- `tests/test_auth.py`: наблюдатель получает 403 на `POST /jobs/dismiss`, инженер проходит, запрос без
  CSRF-токена отклоняется.
- Браузерный прогон в песочнице на локальной TimescaleDB:
  - упавшая задача;
  - строка `running` из «прошлого процесса», вставленная в таблицу;
  - кнопки «Скрыть» и «Очистить» на странице «Новый отчёт» и в архиве;
  - наблюдатель кнопок не видит;
  - опрос прекращается после пометки оборванной задачи.

## 6. Риски и ограничения

- **Список общий.** Инженер скрывает задачи для всех. Кто это сделал, видно в журнале действий. Скрывать только
  свои задачи можно, если сохранять владельца в таблице, но у старых строк владельца не будет. Это отдельная
  доработка.
- **Права на таблицу.** `ALTER TABLE` требует, чтобы таблица принадлежала роли приложения. Так и есть, если
  таблицу создало приложение. Если её заранее создал администратор базы под другой ролью, колонка не появится:
  в логе будет предупреждение, а `POST /jobs/dismiss` ответит 503 с понятным текстом. Остальные функции задач
  продолжат работать.
- **Несколько экземпляров приложения.** Правило оборванных задач опирается на один процесс, как в Docker-образе.
  При нескольких экземплярах живая задача соседа может на время показаться прерванной. Её следующее обновление
  прогресса вернёт статус `running`.
- **Таблица не очищается.** Строки задач хранятся бессрочно, как и сейчас. Автоматическое удаление строк старше
  N дней в план не входит. Его можно добавить отдельной миграцией в `loadlens_app/migrations.py`.
