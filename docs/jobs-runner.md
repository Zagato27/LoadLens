# Фоновые задачи: поток веб-процесса или Celery-воркер

Отчёты и публикации в Confluence строятся в фоне: страница сразу получает номер задачи и опрашивает её состояние. Задачу выполняет либо поток веб-процесса, либо отдельный Celery-воркер. Воркер снимает с веб-процесса тяжёлую работу (pandas, графики, ответы модели): пока строится отчёт, остальные страницы отвечают так же быстро, как без него.

## Что выполняется в фоне

| Задача | Откуда | Имя задачи Celery | `kind` в `report_jobs` |
|---|---|---|---|
| Отчёт | «Новый отчёт» (`POST /create_report`), наблюдатель прогонов страницы «Запуск теста» | `loadlens.report` | `report` |
| Публикация отчёта в Confluence | кнопка на странице отчёта (`POST /publish_confluence`) | `loadlens.publish_confluence` | `confluence` |
| Публикация прогноза в Confluence | страница прогноза (`POST /forecast/<run_id>/confluence`) | `loadlens.publish_forecast` | `forecast_confluence` |

Объяснение прогноза моделью и разбор документа для контекста системы выполняются прямо в запросе, как раньше. Графики Grafana, логи Loki и вложения Confluence отчёт скачивает и загружает сам, своим пулом потоков (до 3 попыток с паузой 2 с, на элемент не больше `CELERY_TASK_TIMEOUT`, 600 с), отдельных задач Celery для них больше нет.

## Режимы

Режим задаёт переменная `LOADLENS_JOB_RUNNER`:

| Значение | Где выполняется задача |
|---|---|
| `auto` (по умолчанию) | В воркере, если задан `CELERY_BROKER_URL` и `CELERY_TASK_ALWAYS_EAGER` не равен `1`; иначе в потоке веб-процесса. В коде `CELERY_TASK_ALWAYS_EAGER` по умолчанию `1`, поэтому без настроек — поток, а в Docker Compose (`CELERY_TASK_ALWAYS_EAGER=0` и брокер из `REDIS_PASSWORD`) — воркер |
| `thread` | Всегда в потоке веб-процесса, как до появления воркера |
| `celery` | Всегда в воркере. С `CELERY_TASK_ALWAYS_EAGER=1` задача выполняется прямо внутри запроса (режим отладки Celery), в журнале предупреждение |

Без установленного пакета `celery` задачи всегда идут потоком. Режим определяется для каждой новой задачи по переменным окружения веб-процесса; чтобы сменить его, перезапустите приложение. Форма ответов `/create_report`, `/publish_confluence`, `/forecast/<run_id>/confluence`, `/jobs` и `/job_status` от режима не зависит.

## Переменные окружения

| Переменная | По умолчанию | Кто читает | Что задаёт |
|---|---|---|---|
| `LOADLENS_JOB_RUNNER` | `auto` | приложение | Режим: `auto`, `thread`, `celery` (см. выше). Неизвестное значение считается `auto` |
| `LOADLENS_JOB_STALE_MIN` | `15` | приложение | Минут без прогресса и heartbeat, после которых начатая задача воркера становится ошибкой «Задача прервана: воркер не отвечает» |
| `LOADLENS_JOB_QUEUE_MAX_MIN` | `120` | приложение | Минут ожидания в очереди, после которых задача, которую не взял ни один воркер, становится ошибкой «Задача прервана: воркер не взял её из очереди» |
| `LOADLENS_REPORT_TASK_LIMIT_SEC` | `3600` | приложение и воркер | Мягкий лимит времени задачи в воркере, секунды: по нему задача завершается ошибкой «Задача прервана: превышено время задачи»; через 60 с после него процесс воркера убивается. Лимит кладёт в сообщение приложение, текст ошибки пишет воркер — задавайте одинаково обоим |
| `CELERY_BROKER_URL`, `CELERY_RESULT_BACKEND` | — | приложение и воркер | Адрес Redis. В Compose собираются из `REDIS_PASSWORD` |
| `CELERY_TASK_ALWAYS_EAGER` | `1` в коде, `0` в Compose | приложение и воркер | `1` — Celery выполняет задачи синхронно; для режима `auto` это значит «поток» |
| `CELERY_TASK_TIMEOUT` | `600` | тот, кто строит отчёт | Таймаут скачивания одного графика, лога или загрузки одного вложения, секунды |
| `WORKER_CONCURRENCY` | `2` | docker compose | Сколько задач воркер выполняет одновременно (процессов) |
| `WORKER_MEMORY_LIMIT`, `WORKER_CPUS` | `2g`, `1` | docker compose | Ограничения контейнера воркера |

Compose передаёт `CELERY_*`, `LOADLENS_JOB_*` и `LOADLENS_REPORT_TASK_LIMIT_SEC` и приложению, и воркеру; пример с комментариями — `docker/env.example`.

## Как задача проходит через воркер

1. Роут проверяет лимиты (`limits.max_parallel_jobs`, `limits.max_parallel_jobs_per_user`, дневной лимит отчётов с ИИ) и пишет строку в `report_jobs`: `status=running`, `runner=celery`, `owner`, пустой `started_at`.
2. Задача уходит в очередь `reports` Redis с `task_id`, равным номеру задачи. Ответ `/create_report` — за 0.1–0.3 с.
3. Воркер берёт задачу, перечитывает `settings_runtime.json`, проверяет строку (задачу, которая уже завершена, снята или начата, не выполняет) и ставит `started_at`.
4. Пока задача идёт, воркер пишет прогресс в строку, а раз в 30 с — heartbeat (обновляет только `updated_at`): долгий ответ модели без прогресса не считается зависанием.
5. Итог (`done` со ссылкой на отчёт или `error` с этапом, на котором всё остановилось) записывается в строку; если таблица не ответила, запись повторяется через 1 и 3 с.
6. Веб-процесс читает строку: `/job_status/<id>` при каждом опросе, `/jobs` через кэш на 3 с.

Сообщение задачи подтверждается при получении (`task_acks_late=False`): упавший воркер не повторит отчёт, задачу пометит проверка зависших (ниже). Время в `created_at`, `started_at`, `updated_at` пишут разные процессы, поэтому часы хостов приложения и воркера должны быть синхронизированы (NTP).

## Сбои

| Что случилось | Что видит пользователь | Что делать |
|---|---|---|
| Воркер упал или убит посреди задачи (OOM, перезапуск контейнера без ожидания) | Через `LOADLENS_JOB_STALE_MIN` минут после последнего обновления задача становится ошибкой «Задача прервана: воркер не отвечает» (проверка идёт при опросе `/jobs` и `/job_status`, не чаще раза в 30 с, поэтому до 30 с позже); страница перестаёт её опрашивать | Запустить отчёт заново. Уже сохранённые метрики прогона остаются: удалите прогон в «Архиве», если он не нужен. Повтора задачи после перезапуска воркера не будет |
| Redis недоступен | `/create_report` отвечает на несколько секунд дольше (таймауты подключения 2 с и ответа 5 с), задача выполняется потоком веб-процесса (`runner=thread`), результат обычный. В журнале приложения: `Could not send job <id> (loadlens.report) to the Celery broker: …; running it in a thread of the web process` | Вернуть Redis. Воркер переподключится сам, следующие задачи снова пойдут в него |
| Перезапуск веб-процесса | Задачи воркера продолжаются и доходят до `done`; задачи потоков веб-процесса при старте отмечаются «Задача прервана: сервер перезапустился во время выполнения» | — |
| Воркер не запущен или занят | Задача висит «В работе» с 0 % и сообщением «Инициализация…», `started_at` пуст; она занимает слот лимита. Через `LOADLENS_JOB_QUEUE_MAX_MIN` минут — ошибка «Задача прервана: воркер не взял её из очереди» | Запустить воркер. Сообщение остаётся в Redis: воркер, запущенный позже, получит его и пропустит (`Not running job <id> … its status is already error`) |
| Задача дольше `LOADLENS_REPORT_TASK_LIMIT_SEC` | Ошибка «Задача прервана: превышено время задачи» | Увеличить лимит или окно отчёта сделать короче. В `--pool=solo` (Windows) лимиты не действуют |
| Таблица задач недоступна, когда воркер пишет итог | Если не помогли повторы через 1 и 3 с, задача остаётся «В работе», пока её не снимет проверка зависших | Причина — в журнале воркера |
| У роли БД нет права изменить старую таблицу `report_jobs` | В журнале предупреждение: колонок `owner`, `runner`, `started_at` нет; задачи воркера не считаются в лимитах, не снимаются проверкой зависших, а перезапуск приложения помечает их прерванными | Выполнить `ALTER TABLE report_jobs ADD COLUMN …` из `docker/initdb/02_schema.sql` от владельца таблицы или запустить `docker/initdb/03_app_role.sh` |

## Ёмкость: очередь, лимиты, память, LLM

- Лимиты `limits.max_parallel_jobs` (4) и `limits.max_parallel_jobs_per_user` (2) считаются по таблице `report_jobs`, включая задачи, которые ждут в очереди. Воркер выполняет `WORKER_CONCURRENCY` (2) задач одновременно, остальные ждут в очереди `reports` в порядке поступления. Чтобы задачи не ждали, держите `WORKER_CONCURRENCY` не меньше `max_parallel_jobs` или запустите ещё один воркер из того же образа с теми же настройками и томами (`docker compose up --scale` не подойдёт: у сервиса задан `container_name`).
- Каждый процесс воркера держит данные одного отчёта; pandas не возвращает память системе, поэтому процесс заменяется после 20 задач (`--max-tasks-per-child 20`). Поднимая `WORKER_CONCURRENCY`, поднимите и `WORKER_MEMORY_LIMIT`.
- Ограничение `llm.<провайдер>.max_concurrent` действует внутри одного процесса. К провайдеру одновременно уходит до `WORKER_CONCURRENCY × max_concurrent` запросов (плюс потоки веб-процесса, если часть задач идёт потоком): проверьте лимиты провайдера.
- `stop_grace_period: 2m` у воркера: при `docker compose stop` идущие задачи успевают закончиться, если укладываются в 2 минуты; остальные пометит проверка зависших.

## Настройки в воркере и обновление

- Воркер читает `settings.py` при старте, а `settings_runtime.json` — перед каждой задачей: изменения со страницы «Настройки» применяются без перезапуска. Ключ, удалённый из `settings_runtime.json`, сохраняет в воркере прежнее значение до перезапуска. После правки `settings.py` или переменных окружения перезапустите и приложение, и воркер. В контейнер воркера runtime-файлы смонтированы только для чтения.
- Приложение и воркер собираются из одного образа. При обновлении пересобирайте и перезапускайте оба сервиса: `docker compose up -d --build app celery_worker`. Иначе старый воркер будет выполнять задачи нового приложения.
- Воркер запускается из каталога приложения (в образе — `/app`): там лежат `settings.py` и пакеты, которые импортирует `loadlens_app.celery_app`.
- Временные файлы (графики, логи) пишутся в `data_collectors/temporary_files`, это общий том приложения и воркера.

## Как смотреть очередь и задачи

```bash
cd docker
# какие задачи выполняются сейчас (id задачи Celery = номер задачи в LoadLens)
docker compose exec celery_worker celery -A loadlens_app.celery_app inspect active
# взятые воркером, но ещё не начатые; ответ воркера; статистика процессов
docker compose exec celery_worker celery -A loadlens_app.celery_app inspect reserved
docker compose exec celery_worker celery -A loadlens_app.celery_app inspect ping
docker compose exec celery_worker celery -A loadlens_app.celery_app inspect stats
# сколько задач ждёт в очереди reports (пароль redis-cli берёт из REDISCLI_AUTH контейнера)
docker exec ltar_redis redis-cli llen reports
# журнал воркера: «Task loadlens.report[<id>] received» и «… succeeded in 40.2s»
docker logs -f ltar_celery_worker
```

Состояние задач в базе:

```sql
SELECT job_id, kind, status, runner, progress, message, created_at, started_at, updated_at
FROM report_jobs WHERE status = 'running' ORDER BY created_at;
```

`runner = 'celery'` и пустой `started_at` — задача ждёт воркер; заполненный `started_at` и `updated_at` не старше минуты — выполняется. Воркер в Compose проверяется healthcheck'ом `celery inspect ping` раз в минуту (`docker compose ps` показывает `healthy`).

## Разработка на Windows

Без Redis ничего настраивать не нужно: режим `auto` выполняет задачи потоком, как раньше. Тесты закрепляют `LOADLENS_JOB_RUNNER=thread` и eager-режим (`tests/conftest.py`).

С воркером:

1. Redis в Docker: `docker run -d --name loadlens-redis -p 127.0.0.1:6379:6379 redis:7.4-alpine`.
2. Переменные для приложения и для воркера (PowerShell; в Git Bash — `export`):

   ```powershell
   $env:CELERY_BROKER_URL = "redis://127.0.0.1:6379/0"
   $env:CELERY_RESULT_BACKEND = "redis://127.0.0.1:6379/0"
   $env:CELERY_TASK_ALWAYS_EAGER = "0"
   ```

3. Приложение — `python app.py`; воркер — в отдельном окне, из корня репозитория:

   ```powershell
   python -m celery -A loadlens_app.celery_app worker --loglevel=info --pool=solo -Q reports,celery
   ```

На Windows работает только `--pool=solo`: один процесс, одна задача за раз (вторая ждёт в очереди), лимиты времени не действуют. Остановка — Ctrl+C (дожидается текущей задачи) или завершение процесса `python.exe`: тогда задачу пометит проверка зависших.

## Проверка

Сквозные проверки лежат в `tools/e2e_jobs/`: каждая сама поднимает сервер песочницы, воркер `--pool=solo` и заглушки из `tools/stubs/`, проверяет свой сценарий по ответам API, журналам и строке `report_jobs` и всё останавливает; подготовка песочницы описана в `docs/perf-baseline.md` («Этап 3»), запуск — в шапке каждого скрипта.

| Скрипт | Сценарий |
|---|---|
| `s1_ui_report.py` | Отчёт со страницы «Новый отчёт» (Playwright): прогресс на странице, `done`, отчёт открывается |
| `s2_publish_confluence.py` | Публикация отчёта в Confluence через воркер |
| `s3_publish_forecast.py` | Публикация прогноза через воркер |
| `s4_worker_killed.py` | Воркер убит посреди отчёта: ошибка «воркер не отвечает», страница перестаёт опрашивать, повтора нет |
| `s5_redis_down.py` | Redis остановлен: задача идёт потоком; Redis вернулся — снова воркер |
| `s6_server_restart.py` | Веб-сервер перезапущен во время задачи воркера: задача доходит до `done` |
| `s7_heartbeat.py` | Долгие ответы модели без прогресса: heartbeat не даёт снять задачу |
| `s8_queue_wait.py` | Вторая задача ждёт занятый воркер; задачу без воркера снимают через `LOADLENS_JOB_QUEUE_MAX_MIN` |
| `bench_modes.py` | Задержки страниц во время отчёта: поток против воркера (`tools/bench_endpoints.py --during-job`) |

Результаты замеров — в `docs/perf-baseline.md`, раздел «Этап 3».
