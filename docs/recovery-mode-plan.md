# План: режим восстановления при недоступном хранилище

Цель: LoadLens запускается и остаётся управляемым, когда база `storage.timescale` недоступна. Страницы
отвечают сразу и понятно, а администратор может войти без базы, исправить подключение и вернуться к
обычному входу. Вход при этом не отключается: аварийная сессия ограничена одной задачей.

**Статус (2026-10-13): реализовано.** Отличия от плана:

- `GET /auth/me` не получил отдельного флага: аварийную сессию отличает `"via": "recovery"`.
- POST-запросы к публичным маршрутам (вход) проверяют CSRF и тогда, когда сессию не удалось определить из-за недоступной базы, и в аварийной сессии.
- `errors.internal_error` и обработчик приложения отдают для `StorageUnavailableError` страницу или JSON 503 без трассировки; фоновые задачи (`loadlens_app/jobs.py`) пишут о сбое одной строкой.
- Если хранилище пропало у вошедшего пользователя, страница может открыться из кэша пользователя (10 с), а её запросы данных получат 503. Тогда интерфейс показывает баннер «Хранилище недоступно», администратору — со ссылкой на `/recovery`.
- Сохранение формы удаляет `dsn` из `storage.timescale`: иначе отчёты продолжили бы ходить по старой строке подключения.
- В `docker/docker-compose.yml` добавлены `LOADLENS_RECOVERY_USER` и `LOADLENS_RECOVERY_PASSWORD_HASH`. Хеш в `.env` берётся в одинарные кавычки.

Проверено тестами (`tests/test_storage_state.py`, `tests/test_recovery_mode.py`) и прогоном в браузере на копии приложения: база на закрытом порту, затем локальная TimescaleDB в контейнере.

## 2. Решения

1. **Предохранитель вокруг `_ts_conn`.** Новый модуль `loadlens_app/storage_state.py` оборачивает подключение:
   таймаут `storage.timescale.connect_timeout_sec` (по умолчанию 5), при отказе состояние «недоступно» с типом
   ошибки, временем и санированным текстом; повторная попытка не чаще `retry_seconds` (по умолчанию 10) и только
   одним потоком, остальные запросы получают кешированный отказ мгновенно. Отказ бросается как
   `StorageUnavailableError(psycopg2.OperationalError)`, поэтому все существующие `except psycopg2.Error`
   и `except Exception` продолжают работать. Успешное подключение сразу переводит состояние в «доступно».
2. **Понятная страница.** HTML-маршруты при недоступной базе получают `templates/storage_unavailable.html` со
   статусом 503: тип ошибки (таймаут, отказ в соединении, неверный пароль, DNS, прочее), время последней попытки,
   что делать и кнопка «Войти для восстановления». API-маршруты получают JSON 503 `storage_unavailable` с
   `Retry-After`. Адрес базы (host:port, имя базы) показывается только аварийной сессии и при выключенной
   авторизации: анонимному посетителю внутренний адрес не раскрывается, в логе он есть всегда.
3. **Аварийный вход.** `GET /login` при недоступной базе не ходит в базу: рисует форму с баннером «Хранилище
   недоступно, доступен только аварийный вход администратора». `POST /login` сверяет логин и пароль с
   `LOADLENS_ADMIN_USER` / `LOADLENS_ADMIN_PASSWORD` (сравнение постоянного времени) либо с
   `auth.recovery_user` + `auth.recovery_password_hash` из `settings.py` (scrypt-хеш, выдаётся командой
   `python -m loadlens_app.auth hash-password`), чтобы в файле не лежал пароль открытым текстом. Успех — сессия
   `{"recovery": 1, "iat", "csrf"}` на 30 минут без продления, запись в лог с IP. Неудача — общий ответ 503
   «Хранилище недоступно; обычный вход невозможен» без уточнения причины, учёт попыток в `LoginThrottle`
   (5 за 5 минут на IP и логин) плюс общий потолок на процесс (20 неудач за 5 минут), каждая попытка в логе.
   Если аварийный администратор не настроен, форма входа заменяется инструкцией: какую переменную окружения или
   какой ключ `settings.py` задать. Аварийный вход работает только пока база недоступна: при доступной базе те же
   данные идут обычным путём через таблицу пользователей.
4. **Узкие права.** Аварийная сессия — `AuthContext(user=None, role=ADMIN, via="recovery")`, но шлюз пропускает
   её только на явный список маршрутов: страница `/recovery`, `GET /recovery/status`, `POST /recovery/storage/check`,
   `POST /recovery/storage/save`, `POST /logout`, `GET /auth/me`, статика и логотип. Всё остальное — 403
   «Недоступно в аварийном режиме». Страница `/recovery` повторяет карточку «Хранилище»: те же поля, маска `***`,
   «Проверить соединение» через `check_timescale`, «Сохранить» через `store_section("storage.timescale")`.
   Отдельный небольшой `static/js/recovery.js`, а не урезание `settings.js`: страница настроек тянет промпты,
   проекты и пользователей, которых без базы нет, и слишком легко по ошибке открыть лишнее. Все действия
   аварийной сессии пишутся в лог приложения (`loadlens_app.auth.recovery`) с IP: вход, проверка (только хост и порт),
   сохранение (хост, порт, база, пользователь без пароля), выход.
5. **Автоматический выход.** На каждом запросе аварийной сессии шлюз смотрит состояние предохранителя. Как только
   база доступна (успешное подключение после сохранения или очередная проверка), сессия очищается и браузер
   уходит на `/login?recovered=1` с сообщением «Хранилище снова доступно, войдите обычным способом». Истёкшая
   аварийная сессия тоже очищается. После успешного сохранения `/recovery/storage/save` сам делает пробное
   подключение, перечитывает репозиторий пользователей (адрес берётся из `CONFIG` при каждом обращении, менять
   ничего не нужно) и отвечает `{"ok": true, "redirect": "/login"}`.
6. **Аудит без базы.** `_after_request` не вызывает `service.audit`, пока хранилище недоступно (иначе каждое
   действие ждало бы отказ); вместо этого пишет строку в лог. Когда база вернётся, обычный аудит продолжается.
7. **Выключенная авторизация** (`LOADLENS_AUTH_ENABLED=0`): страница «Хранилище недоступно» и `/recovery`
   доступны всем, как и остальные настройки сегодня; адрес базы показывается, так как посетитель и так
   администратор. Поведение документируется, ничего нового не открывается.

## 4. Тесты

- `tests/test_storage_state.py`: таймаут передаётся в `psycopg2.connect`; после отказа повторные вызовы в окне
  `retry_seconds` не трогают сеть; одна полуоткрытая попытка; успех сбрасывает состояние; классификация ошибок;
  в сообщении нет пароля.
- `tests/test_recovery_mode.py` (Flask-клиент с репозиторием, который бросает `StorageUnavailableError`):
  HTML-маршрут → 503 страница без адреса базы для анонима; API → JSON 503 с `Retry-After`; `/login` открывается
  без базы; неверные данные → 503 без уточнения, после 5 попыток — 429; верные данные → аварийная сессия и
  редирект на `/recovery`; без настроенного администратора — инструкция; аварийная сессия получает 403 на
  `/config`, `/settings`, `/auth/users`; `/recovery/storage/check` зовёт `check_timescale` с данными формы,
  `***` подставляет сохранённый пароль только при прежнем адресе; `save` пишет `settings_runtime.json`, делает
  пробу и при успехе завершает сессию; при доступной базе аварийная cookie сбрасывается с редиректом на `/login`;
  срок 30 минут; хеш из `settings.py` принимается, bootstrap-данные при доступной базе работают как раньше;
  `LOADLENS_AUTH_ENABLED=0` — страница доступна, адрес виден.
- `tests/test_auth.py`: правила для новых маршрутов, матрица ролей, `recovery_ok` только у разрешённых.
- Браузерный прогон в песочнице с базой на закрытом порту `127.0.0.1:9` и на несуществующем адресе (таймаут):
  страница 503, вход, страница восстановления, проверка, сохранение адреса локальной TimescaleDB из `docker/`,
  автоматический выход и обычный вход.

## 6. Риски и ограничения

- Тротлинг аварийного входа живёт в процессе: при нескольких воркерах gunicorn лимит умножается на их число.
  Блокировки учётной записи в базе нет по определению. Лимиты поэтому жёстче обычных, и каждая попытка в логе.
- Аварийные учётные данные в переменных окружения — те же, что у bootstrap, и README уже советует убрать
  `LOADLENS_ADMIN_PASSWORD` после первого входа. Для постоянной готовности к восстановлению рекомендуется хеш в
  `settings.py`, а не пароль в окружении.
- Предохранитель общий на процесс: пока он «разомкнут», любой запрос к базе получает отказ без попытки, даже если
  база только что поднялась; задержка не больше `retry_seconds`.
- Страница 503 для анонима не показывает адрес базы. Если нужно показывать его всем, это одно условие в шаблоне,
  но тогда внутренний адрес виден любому, кто дойдёт до сервера.
- Фоновые задачи (отчёты в потоках, Celery) используют тот же `_ts_conn` и получат быстрый отказ вместо долгого
  ожидания; их обработка ошибок не меняется.
